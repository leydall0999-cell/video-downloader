一、为什么会一直失败（原来只差两半）

以前 VDL 的 YouTube 是两头都走不通：带登录态卡在 The page needs to be reloaded，不带则被 bot 拦截。 对标 DataTool 静态分析 + 本机 A/B 实测后确认，它稳定靠的是两半互补的机制，而我们此前两半都缺。

二、决定性证据（同机 / 同代理 / 同 Cookie，video=YK9a6TC9j54）

组合结果
实时浏览器会话 + 无 JS runtime❌ The page needs to be reloaded（卡死）
实时浏览器会话 + deno + EJS✅ 解析成功（35 格式，含 4K）
缓存快照 + deno + EJS❌ 仍 bot 拦截
⇒ 两半缺一不可。只补 JS runtime、或只换新鲜 Cookie，单独做都还是失败。

三、这次改了什么

半改动
① 会话自持 Cookie 候选顺序改为 user > env > browser > cache > pool； 实时浏览器会话插到 30 天 TTL 的缓存之前（Google 靠 5 个滚动字段判会话死活， 快照一落后就被判未登录，而缓存会一直挡在新鲜值前面）。 新增登录态体检（只认 SID/__Secure-1PSID/__Secure-3PSID/LOGIN_INFO）与 精确报错（「浏览器里的登录态不可用」而非笼统「需要 Cookie」）。
② JS 挑战求解 新增 runtime 定位（_MEIPASS/bin → venv → PATH）与挑战选项下发 （按 yt-dlp 注册表过滤，硬编码会让它直接报错）； 打包带上 yt-dlp-ejs + deno 二进制。 关键坑：yt-dlp 的 --js-runtimes 默认只启用 deno， 不会自动找 PATH 里任何 JS runtime。

六、一个需要如实说明的边界

本次修复的是桌面端：它用的是本机浏览器的实时会话（同机同 IP，YouTube 认）。 网页版走的是机房 IP、Cookie 需要跨机回放，那条路上 YouTube 仍判 LOGGED_IN:false —— 这个老结论没有被本次修复改变，别用它推断网页版能下 YouTube。
另外 YouTube 有逐视频的登录要求（部分视频对任何下载器都要求登录）， 那种情况会明确报「登录态不可用」或需要登录，属视频本身策略，不是本 app 的缺陷。
