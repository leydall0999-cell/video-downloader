一句话结论

它的网页下载不是靠"服务端帮你下好"，而是把下载这件事放到浏览器里干：分片并发拉、失败自动重试、HLS 在浏览器里合成 MP4、防盗链用轻量中继绕。 我们正好相反——能直连就一个单连接裸下（没进度没重试），不行就整包甩给服务端。

于是最有价值的借鉴只有一条主线：把「浏览器侧下载」从"点一下听天由命"升级成"分片 + 并发 + 进度 + 重试"，再配一个媒体中继兜住防盗链。这一条同时省服务端带宽、提升成功率、还让用户看得见进度。其余（浏览器内 m3u8→MP4、画质分级 PRO 角标）是第二梯队。

二、我们现在的下载是什么样

路径实现评价
直链下载 web/app.js 的 triggerDirectDownload()：建一个 <a download> 点一下 单连接、无进度、无重试；源站防盗链就失败，得让用户手动切「改用服务器下载」
服务端下载 POST /api/download 建任务 → 服务端 yt-dlp 拉完 → 浏览器取文件 能力最全（见下），但服务端要扛出口带宽与转码
HLS 处理 全靠服务端；直链已明确排除 HLS（_detect_direct_url() 要求 info['direct'] + http(s) + 直链扩展名） 不会误存成 .m3u8 文本（这点是对的），但 HLS 的活全压在服务器

四、值得借鉴的（按性价比排序）

优先级搬什么怎么做 / 注意什么
★★★ 直链下载升级为「分片 + 并发 + 进度 + 重试」 改 triggerDirectDownload()：先 HEAD 取长度 → 10MB 分片 → 3 并发 Range 请求 → 失败重试 3 次 → 进度条。 坑：跨域 Range 要源站给 CORS 且暴露 Content-Length，拿不到就自动退化单流——这正是对方为什么必须配中继。
★★★ 加媒体中继 /api/proxy/media 防盗链/CORS 时由自己服务器带 Referer/UA 转发。有了它，「源站拒绝直连」就从"失败"变"能下"，也让大文件下载留在浏览器侧、减轻 ECS 出口压力。
★★★ 画质分级付费钩子（PRO 角标） 后端在变体上标 need_vip（原画档），前端出 PRO 角标。免费给 1080P、付费给原画。我们会员中心/激活码/配额都现成，只差这一步就能变现。
★★ 浏览器内 m3u8 → MP4 拉 init 段 + 全部 ts 并发合成 Blob（纯 JS，快、无转码）；复杂流再上 ffmpeg.wasm。价值是把 HLS 的转码/出口成本从服务器挪走。注意我们直链已排除 HLS，所以这是"新增能力"而非修 bug，收益主要体现在服务端下载路线。
★★ 格式过重时引导装客户端 把"网页端搞不定的重型格式"做成明确提示 + 一键去下载页，既是降级也是导流。我们只是被动提示"改用服务器下载"。
★ 一次解析返回 视频/音频/图片 三类 + 图集下载 对齐 Instagram/小红书轮播这类"一次多文件"的场景；我们的图片能力目前在别的 tab，可以打通。
★ 失败降级链 + 封面健壮性 中继 → 分片 → 单流 → 右键另存窗口；HEIC 封面转码、封面 404 重取。属于"稳"的细节。

五、我们不该动摇的优势

把上面看完容易产生"我们哪哪都不如"的错觉，其实相反——我们网页版的下载骨架比它强：

  • 服务端任务队列：任务卡 + SSE 实时进度 + 暂停 / 续传 / 重试 / 取消。它是纯客户端下载，断网就得重头再来，没有队列、没有续传。
  • 可调并发数、多下载器选择、播放列表批量。它是一个下载按钮打天下。
  • 线路切换（国内 / 海外双节点）+ Cookie / 代理高级项。它服务端在海外、能力单一；我们能干"需要登录态、需要指定出口"的活。

所以正确姿势是补齐"浏览器侧那一半"，而不是把服务端那一半拆掉。两边各干各擅长的事：能直连的走分片并发（便宜、快、有进度），搞不定的甩服务端（能力全、能兜底）。

建议落地顺序

  1. 第一步（最划算）：直链改分片并发 + 进度 + 重试，同时加 /api/proxy/media 中继兜防盗链。这两件必须一起做，否则分片在跨域下拿不到长度、退化成单流，等于白改。
  2. 第二步：画质分级 PRO 角标 —— 后端数据（会员/配额）全都有，只加展示与扣次，变现最快。
  3. 第三步：浏览器内 m3u8→MP4，把 HLS 的服务端成本挪到客户端；优先级低于前两步，因为影响面主要在服务端下载路线。
  4. 第四步：混合媒体 + 图集、导流提示、降级链收尾。
